## Why

When a session dies on the backend (logout on another device, admin disable/ban, user deleted, `JWTSecret` rotated, session evicted by the 5-session cap) the `refresh_token` and `session_id` cookies stay in the browser until their `Max-Age` ends. `src/proxy.ts` only checks that both cookies exist, so it keeps redirecting `/{locale}` to `/{locale}/home`, where `SignedInHomePage` ends on the "Login required" block. Nothing ever deletes the dead cookies: the Next refresh proxy (`src/app/api/auth/refresh/route.ts`) and the server-writable branch of `attemptRefresh` (`src/api/transport/api-transport.ts`) both return the failure without clearing them. The user can never see the public home again until they sign in or clear cookies by hand.

The same fix is also the prerequisite for caching the public home in a later change: the guest home can only be cached safely when a dead cookie cannot pin a visitor to the signed-in redirect.

Review of the dashboards and `/home` found a second, related defect on the same path (Phase 2). A failed current-user lookup is indistinguishable from a guest: a `/me` that answers 5xx, times out or cannot connect, and a `/me` 401 whose refresh then fails with 5xx or a timeout (the transport rethrows the original 401, so `getMeService` returns `null`), both end as `me = null`. The dashboards then show "Sign in required" and auto-open the login modal, and `/home` and `become-instructor` show their sign-in prompts, although the session is valid and the cookies are intact. A backend blip should show a retryable error, not ask the user to sign in again. The three sign-in gates also use three different layouts (shared `StatusErrorPage` on dashboards, a bespoke block on `/home`, an emoji `StateCard` on `become-instructor`).

## What Changes

- The browser refresh proxy `POST /api/auth/refresh` clears all auth cookies when the backend rejects the refresh with HTTP 401 or 403 (a genuinely dead session), and tells the client that it cleared them. It keeps the cookies on 400, 429, 5xx, timeout, network error and on FE-side parse failures (no sign-out on backend flakiness).
- The server-writable refresh branch (Server Actions) applies the same rule through a new optional `clearSession` callback on the `server-writable` runtime adapter. To make that possible `refreshUpstreamSession` keeps the upstream HTTP status on its typed error instead of dropping it.
- The status-to-"session is dead" decision lives in one shared helper used by both the route and `attemptRefresh`, so the two paths cannot drift.
- Browser refresh takes a cross-tab lock (`navigator.locks`, with a no-lock fallback) so two tabs never rotate the same refresh token concurrently; a tab that waits then refreshes with the cookie the other tab just wrote.
- When the refresh proxy reports that it cleared the cookies, the client broadcasts the existing `logout` event with `reason: "session_expired"`; other tabs react through the existing `useAuthLogoutTabSync` (revalidate `/me`, reload) and land on the public home through the proxy. The event is sent only when cookies were really cleared, never when cookies were missing or the failure was transient.
- **Phase 2, data layer.** A browser refresh that fails with HTTP 429/5xx, a timeout or no connection is marked on `BrowserRefreshResult` (`outage`) and the transport rethrows the original 401 as `ApiSessionUnverifiedError`, a subclass of `ApiHttpError` (status 401, so every existing 401 check still matches) that carries the outage. `getMeService` rethrows it instead of returning `null`; a plain 401 still means guest. `classifyApiError` maps it to `network` / `server-error`; `reportApiError` stops treating it as guest noise.
- **Phase 2, presentation.** New `useMeOutage()` (derived from `useGetMe()` + `classifyApiError`, only when no user is cached) and new `MeOutagePage` (the shared `StatusErrorPage` with the existing `errors.boundary.retry` label and `mutateMe`). Dashboards (`DashboardLayout`), `SignedInHomePage` and `BecomeInstructorPage` show it for an outage and no longer auto-open the login modal for it. A 403 or 404 `/me` keeps today's handling.
- **Phase 2, shared sign-in gates.** `SignedInHomePage` and `BecomeInstructorPage` (state A) render the shared `StatusErrorPage variant="unauthorized"` like the dashboards, with their existing copy (`loginRequired.*`, `stateA.*`), so tests and e2e assertions on "Sign in to continue" stay valid. User-approved exception to the earlier "do not touch `SignedInHomePage`" rule, limited to this edit.
- No change to `src/proxy.ts`, the redirect helpers, caching, ISR, `generateStaticParams`, `Vary` headers or `SEO_TEMPORARY_ENV_CACHE_POLICY` (stays `enabled: false`, marked KEEP). Guest-looking chrome during an outage (header `AuthLayout`, sidebar footer, Google One Tap, `BecomeInstructorPromoBanner`) and Server Action refresh outages are recorded as follow-ups, not changed.
- No backend change. The backend `rotateSession` race (read-check-write without compare-and-swap) is recorded as a follow-up for the backend repository.
- Tests first: new route handler test, new transport test cases for the server-writable branch, new tests for the lock and the broadcast; for Phase 2 new tests for the outage flag, the error subclass, `getMeService`, `useMeOutage`, `MeOutagePage`, the three gated screens and one e2e case (backend 500 on `/me`); documentation updates in English.

## Capabilities

### New Capabilities
- `auth-session-recovery`: what the frontend does when a refresh is rejected (which statuses clear the session cookies, which never do, how a cleared session is signalled to other tabs, and how concurrent refreshes across tabs are serialised) and, in Phase 2, how a refresh or lookup that could not conclude is told apart from a guest.

### Modified Capabilities
- `signed-in-home-entry`: the requirement "Stale cookie does not trap the user" changes from "the user sees the sign-in prompt on every visit" to "the dead cookies are removed after the failed refresh, so the next visit to `/{locale}` serves the public home"; with the backend failing, `/home` shows a retryable state instead of the sign-in prompt (Phase 2).
- `signed-in-home`: "Login gate on the signed-in home" now names the shared `unauthorized` state and adds the outage state (Phase 2).
- `dashboard-access-control`: "Denial reason determines which full-page state renders" adds the outage state, and "Unauthenticated denial automatically prompts login" excludes it (Phase 2).
- `frontend-error-handling`: three ADDED requirements (sign-in gates use the shared unauthorized state; a failed current-user lookup renders a retryable status-aware state; the classification covers an unverified session) (Phase 2).
- `frontend-regression-coverage`: the authentication regression requirement and the critical browser journeys requirement gain the stale-session cases introduced by this change.
