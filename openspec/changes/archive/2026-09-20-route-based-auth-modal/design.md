## Context

See proposal.md - Why. Today the login/sign up modal is a single Radix `Dialog` (`LoginSignupPopup`) controlled by a global Zustand store (`authAction`, `nextLink`), mounted redundantly in `header.tsx`, `dashboard-layout.tsx`, and `auth-layout.tsx`. `nextLink` only ever receives hard-coded internal constants today (`PRIVATE_ROUTES.home`, `PUBLIC_ROUTES.becomeInstructor`), never a value read from the URL, so there is currently no open-redirect surface, only a missing-feature gap (the header's own "Sign in" button opens the modal with no return path at all). Every dashboard permission gate is client-side, inside `DashboardLayout`; `src/proxy.ts` is the project's one middleware entry (next-intl locale enforcement only, matcher already excludes the locale-less OAuth callback routes) and this change does not touch it, since `/login`/`/signup` live under `[locale]` like every other routed page. OAuth (Discord, Google) runs through a popup window and `postMessage` relay (`OAuthPopupCallbackRelay`); the main tab never unloads during that flow, so in-memory/URL state on the main tab already survives it today. The app uses `next-intl` with `localePrefix: "always"`; all routing must go through `@/i18n/navigation`'s locale-aware `Link`/`useRouter`, not the raw `next/navigation` versions (query-string reads are the one exception - see Decision 3).

Six existing `docs/*.md` files describe the current architecture in enough line-level detail that they will be wrong, not just incomplete, once this ships: `docs/router.md` (App Router Tree, Guest `/` vs signed-in `/home` section), `docs/pages.md` (Auth flow table, Area/Status table), `docs/screens.md` (Auth Shell section, component tree diagrams, `/home` screen notes), `docs/components.md` (`LoginSignupPopup`/`AuthButton`/`AlertDialog` z-index cross-reference entries), `docs/flow.md` and `docs/logic-flow.md` (sequence diagrams and the `openLoginModal`/`nextLink` action table), and `docs/reusable-assets.md` (the `useAuthStore` asset entry and its "Reuse Rule"). `docs/patterns.md` also shows `openLoginModal` as the canonical example of the store-import pattern. All of these need their outdated content replaced (not appended to) as part of this change, per the project's documentation-sync convention (`docs/router.md`'s own "Adding a New Page" checklist already requires `docs/screens.md`/`docs/pages.md` updates for any new route).

Existing, directly reusable building blocks discovered while designing this change (use these instead of writing new equivalents):
- **Query param reading**: `useSearchParams` from `next/navigation` is already the project's convention for reading a single URL param in a dedicated hook (see `src/hooks/instructor/use-instructor-roster-portfolio-query.ts`: a pure `isValid*` predicate + a hook combining `useSearchParams`/`usePathname`/`useRouter` that clears an invalid value via `router.replace`). The `next` param hook should mirror this exact shape instead of inventing a different one.
- **Path/query building**: `buildQueryParams` in `src/lib/utils/url.ts` already assembles a path + encoded query string; use it to build `/login?next=...` links instead of manual template strings.
- **URL validation style**: `src/lib/instructor-application/url-validation.ts` shows the project's existing convention for a small, pure, unit-tested URL-shape predicate (there for validating an *external* profile URL is `http(s)`; this change needs the mirror-image check that a path is *internal*). Same file organization style, different folder (this one is a security concern, see Decision 3).
- **SEO/noindex scaffolding**: `src/constants/seo/routes.ts` (`SEO_INDEXABLE_PUBLIC_ROUTE_KEYS`), `src/lib/seo/indexable-routes.ts`, and `src/lib/seo/robots-presets.ts` (`robotsModeForPublicRouteKey`, `robotsPreset`) already exist specifically to mark a `PUBLIC_ROUTES` key as `noindex` when it is not in the indexable allow-list - today unused by any page. `confirm-email` and `logout` already show the exact `generateMetadata` + `getTranslations` pattern to mirror for a page title (see `docs/seo-ranking-setup.md`'s A18 entry).
- **Modal chrome**: `LoginSignupPopup`, `LoginSignupLayout`, `LoginContent`, `SignupContent`, and `AuthSocialLogin` need no visual or structural changes - only how they learn "which form" and "what to do on close/success" changes (see Decision 7). The a11y constraint already documented in `docs/components.md` (`DialogTitle`/`DialogDescription` must stay inside `DialogContent`, never siblings under `Dialog` root) still applies and must not regress.

## Goals / Non-Goals

**Goals:**
- Give login/sign up a real URL, addressable by intercepting route when reached by in-app navigation, and by a full page otherwise.
- Make the post-login return path travel in that URL, validated before use.
- Make the dashboard's `unauthorized` denial state actually prompt login automatically instead of relying on the visitor to find the header button.
- Collapse the three redundant `LoginSignupPopup` mounts into a single `@modal` slot.
- Make a hard load of `/login`/`/signup` with a valid `next` render the same intercepted-modal-over-real-background experience as a soft navigation, instead of a bare full page.
- Make the dashboard's auto-prompt re-arm on a genuine page refresh instead of staying silently suppressed for the rest of the tab session once already shown.

**Non-Goals:**
- No change to the dashboard permission-check logic itself (`useSatisfiesPermissions`, the `forbidden` path) beyond leaving it exempt from the new auto-prompt.
- No server-side/middleware auth gate. The gate stays client-side, as today.
- No change to the OAuth popup/`postMessage` mechanism.
- No new pages for `PRIVATE_ROUTES.account.*` (my-courses, my-cart, wishlist, notifications, account-settings) - those pages do not exist yet in `src/app`, so there is nothing to gate.

## Decisions

### 1. Parallel route slot location: `src/app/[locale]/layout.tsx`
`admin`, `instructor`, `sysadmin`, and `(web)` are all direct children of `[locale]`. Placing a single `@modal` slot at `[locale]/layout.tsx` (rendering `{children}` and `{modal}` side by side) lets one `(.)login` / `(.)signup` intercepting pair cover every route in the app, matching how intercepting-route matching works off the `@modal` folder's own position in the segment tree, not the depth of the page the visitor is currently on. Alternative considered: a `@modal` slot per route group (`(web)/@modal`, `admin/@modal`, ...) - rejected, it would triple the boilerplate for no behavioral benefit here.

### 2. `next` as a query parameter, read via a dedicated hook mirroring `useInstructorRosterPortfolioQuery`
`next` is not a secret; it is an internal path. Putting it in the URL (`/login?next=<path>`) is the only option that survives a hard refresh of the full-page `/login` fallback and that a shared/bookmarked login link can carry. `sessionStorage`/`localStorage`/cookies were considered and rejected: none of them are required for the OAuth round trip (popup-based, main tab never unloads), and a cookie in particular would auto-attach to unrelated requests for no benefit here. Reading it is a new `useAuthNextParam()` hook that copies the exact shape already established by `src/hooks/instructor/use-instructor-roster-portfolio-query.ts`: `useSearchParams` (`next/navigation`) + the Decision 3 validator as the pure predicate, `usePathname`/`useRouter` (`@/i18n/navigation`) to strip an invalid value from the URL via `router.replace`. Building the `/login?next=...`/`/signup?next=...` links reuses `buildQueryParams` (`src/lib/utils/url.ts`) instead of manual template strings.

### 3. Internal-path validation, not a route allowlist - lives beside the other FE web-security helpers
Given the number of routes (`PRIVATE_ROUTES` has ~25 leaf paths today and will grow), validating structurally (must start with a single `/`, must not contain `://`, must not start with `//` or a backslash) rather than matching against an enumerated allowlist. This is the standard open-redirect mitigation for this shape of problem and does not need updating every time a route is added. The validator is a single shared function (e.g. `isSafeInternalPath` in `src/lib/security/web/safe-redirect.ts`, alongside the existing `crawl-policy.ts`/`redact-client-payload.ts`/`sanitize-json-ld.ts` in that same folder, following the same "small pure predicate + unit test" style as `src/lib/instructor-application/url-validation.ts`) reused by: the `useAuthNextParam()` hook (Decision 2), the dashboard auto-redirect, and both component-level gates (`SignedInHomePage`, `BecomeInstructorPage`) - replacing three separate call sites that pass a raw path today. `docs/security-hardening-notes.md`'s Helpers table gets a new row for it.

### 4. Auto-prompt delay: fixed 500ms, cancellable, and remount-safe via in-memory (not `sessionStorage`) tracking
On first render of the `unauthorized` denial state, start a 500ms timer; on fire, navigate to `/login?next=<denied path>`. The timer is cleared on unmount and if the resolved auth state changes before it fires. Two things had to be guarded against, both found by manually exercising this in a browser (not caught by the jsdom unit tests, which never remount the component mid-test):
- `usePathname()` itself changes to `/login` once that route is intercepted as a modal, because `DashboardLayout` stays mounted underneath it (it's the `children` behind the `@modal` slot). The denied path is frozen using React's "store info from a previous render" pattern (a `setState` call guarded by a render-time condition, not a ref mutated during render - the latter is a hard error under this repo's `react-hooks/refs` lint rule) the moment the denial state first appears, so the scheduled/fired navigation always targets the original page, not `/login` itself (which would otherwise produce `/login?next=/login`).
- Dismissing the modal (`router.back()`) navigates back to the denied page, but that **remounts** `DashboardLayout` (it is not preserved as a live instance across that round trip in the App Router) - a fresh component instance's state alone would let the 500ms timer schedule and fire again immediately. A module-level `Set` (`autoPromptedPaths`, in-memory, not persisted) keyed by the denied path survives that in-place remount because the JS module itself is not re-evaluated, so the prompt still fires at most once per denied path per page load. Deliberately **not** `sessionStorage`: that would also survive an actual browser refresh of the denied page, permanently suppressing the prompt for the rest of the tab session - the desired behavior is the opposite, a genuine refresh should re-arm it (see Risks/Trade-offs).

### 5. Closing the modal: animate out, then `router.back()`
Radix's `Dialog` plays its exit animation only while the component stays mounted with `open` toggled to `false`; removing it from the tree immediately (as a naive `router.back()` on click would, since it drops the `@modal` slot's content) skips that animation. The close control instead sets local `open=false` first and calls `router.back()` after the transition completes (matching the existing `duration-100` set on `DialogContent`/`DialogOverlay`). `DialogContent` already renders through `DialogPortal` (portals to `document.body`), so moving the single mount point to the root `[locale]/layout.tsx` does not change its DOM position or z-index stacking relative to dashboard/header chrome.

### 6. Login/sign up switch: `router.replace`, not `push`
Switching forms inside the modal uses `router.replace` (preserving `next`) so the browser's back button exits the modal in one step regardless of how many times the visitor toggled between the two forms, instead of walking back through each toggle as separate history entries.

### 7. Reuse `LoginSignupPopup`/`LoginSignupLayout`/`LoginContent`/`SignupContent` as-is; only decouple them from Zustand
No new modal component is written. `LoginSignupPopup` keeps its exact Dialog markup, overlay/content z-index classes, `DialogClose` button, and the `DialogTitle`/`DialogDescription`-inside-`DialogContent` a11y structure - the only change is where it gets `type` ("login"/"signup") and its close callback from: today it reads `authAction`/`closeAllModals` from `useAuthStore`; after this change it takes them as props, supplied by the intercepting `(.)login`/`(.)signup` pages (which are always "open" by construction - they only render when that route is active). The full-page `/login`/`/signup` routes render `LoginSignupLayout` + `LoginContent`/`SignupContent` directly, without the `Dialog`/`DialogPortal` wrapper, since a full page is not an overlay. `LoginContent`/`SignupContent`/`AuthSocialLogin` keep their internal form logic untouched; they only stop reading `nextLink`/`closeAllModals` from `useAuthStore` and instead receive/read the validated `next` value (Decision 2) and a success callback from their new callers. This is a strictly smaller diff than introducing a parallel modal implementation.

### 8. `/login` and `/signup` reuse the existing SEO noindex scaffolding instead of new metadata code
Add `login` and `signup` keys to `PUBLIC_ROUTES` (`src/constants/route.ts`) - publicly routable, like `forgotPassword`/`confirmEmail`/`logout` - and do **not** add them to `SEO_INDEXABLE_PUBLIC_ROUTE_KEYS` (`src/constants/seo/routes.ts`). Each page's `generateMetadata` mirrors the existing `confirm-email`/`logout` pattern (`getTranslations` for `title`) and additionally sets `robots: robotsPreset(robotsModeForPublicRouteKey("login" | "signup"))` (`src/lib/seo/robots-presets.ts`), which already resolves to `"noindex"` for any `PUBLIC_ROUTES` key absent from the indexable allow-list. This is the first page wiring for that previously-unused SEO scaffolding (per `docs/seo-ranking-setup.md`, it existed "for future `generateMetadata`" use) - no new robots logic is written. `docs/seo-ranking-setup.md`'s "Public-routable vs SEO-indexable" section gets `login`/`signup` added alongside `forgotPassword`/`confirmEmail`/`logout`.

### 9. Full removal of `authAction`/`nextLink` from `useAuthStore`
Once every call site (`auth-button.tsx`, `login-content.tsx`, `signup-content.tsx`, `use-oauth-post-auth.ts`, `signed-in-home-page.tsx`, `become-instructor-page.tsx`, `test-support/reset-stores.ts`) is migrated to route navigation, the old fields/actions are deleted rather than kept as a compatibility shim, per the no-dead-state convention already used elsewhere in this store (`MeStoreState` has no legacy fields). `useMeStore` (session/permissions data) is untouched.

### 10. GitNexus impact analysis gates each symbol edit; documentation is replaced, not appended
Per this repo's `AGENTS.md`, before editing any existing symbol touched by this change (`DashboardLayout`, `useAuthStore`/`AuthStoreState`, `LoginSignupPopup`, `AuthButton`, `LoginContent`, `SignupContent`, `useOAuthPostAuth`, `SignedInHomePage`, `BecomeInstructorPage`), run `gitnexus_impact({ target, direction: "upstream" })` and stop to flag any HIGH/CRITICAL result before proceeding. After the implementation, `gitnexus_detect_changes({ scope: "all" })` must confirm the changed-symbol/process set matches this design before considering the change done, and `npx gitnexus analyze` re-syncs the index. All eight `docs/*.md` files identified in Context must have their outdated `LoginSignupPopup`/`authAction`/`nextLink` content replaced with the new route-modal behavior (not left alongside it), matching this repo's existing "update `docs/screens.md`/`docs/pages.md` for a new route" convention in `docs/router.md`.

### 11. Hard-load modal-over-background via a "bounce" bridge, not a manual route-content registry
A hard navigation to `/login?next=X` (typed URL, refresh, shared link) cannot be intercepted by the `@modal` convention - interception is a Next.js App Router feature that only ever engages for a soft (client-side) navigation, by design; there is no supported way to make a hard load render an intercepted route. Two approaches were considered to still show the dimmed-backdrop-modal-over-real-background experience on a hard load:
- **Manually resolve and render `X`'s page/screen component inline inside `/login`'s own page tree** (a hand-built path-to-component registry). Rejected: would need to special-case every dynamic route segment (`/instructor/courses/:courseId/...`), duplicate routing logic Next.js already owns, and drift out of sync as routes are added.
- **Bounce through the background page, then reopen the modal as a soft navigation** (chosen): `useAuthModalBackgroundBridge()` (mounted once, app-wide, in `AppProviders` via `AuthModalBackgroundBridge` - the same "invisible sync component" pattern as the existing `AuthConfirmTabSync`/`AuthLogoutTabSync`) detects, on its first effect run only, that the current route is `/login`/`/signup` with a validated `next`. It `router.replace`s to `next` first (so that page's real content actually renders - e.g. the dashboard's own `unauthorized` denial page), then immediately `router.push`es back to the login/signup destination - which Next.js now intercepts as a modal, since this second navigation is a soft one away from an already-mounted page. The "first effect run only" guard (a ref) is essential: without it, the second navigation (landing back on `/login`) would re-trigger the same bounce logic in an infinite loop.

This reuses `useAuthNextParam()` (Decision 2) for the validated `next` read, so the bridge can never bounce to a cross-origin or otherwise unsafe target - the exact same guarantee already relied on everywhere else `next` is used. It is a per-app-mount side effect, not a per-feature one, so any future route-modal-with-`next` feature can reuse the identical pattern (or this same bridge, if it also targets `/login`/`/signup`) without new plumbing.

## Open Questions

- The bounce (Decision 11) briefly paints the plain, non-modal `/login`/`/signup` full page before the two internal navigations land - accepted as a minor, unavoidable flash for this technique, but not measured against a target frame budget. If it proves visually distracting in practice, a follow-up could hide the full page's own content behind a lightweight loading state whenever a valid `next` is present (deferring to the bridge to decide what to show), without changing the underlying bounce mechanism.

## Risks / Trade-offs

- **[Risk]** Intercepting routes only intercept a *soft* (client-side) navigation; a `router.replace`/`router.push` fired from inside a `useEffect` on first mount of a freshly hard-loaded page still counts as a soft navigation once that page has hydrated, so the dashboard auto-prompt will correctly render as a modal over the already-rendered `unauthorized` page. → No mitigation needed, this matches the intended behavior (denial page renders first, modal opens after 500ms as an overlay on it).
- **[Risk]** A visitor could disable JavaScript timers or otherwise never reach the auto-prompt. → The `unauthorized` denial page still functions as their fallback: `dashboard-access-control`'s existing requirement that the header's sign-in entry point remains visible is untouched, so manual login is still reachable.
- **[Risk]** Removing `authAction`/`nextLink` is a breaking change to `useAuthStore`'s public shape. → Mitigated by doing the removal only after every internal call site is migrated (tasks.md sequences this), and by grepping the codebase for `useAuthStore` usages as a final check before deleting the fields.
- **[Trade-off]** A real `/login` and `/signup` page (even `noindex`) means these paths now exist as crawlable-by-URL, bookmarkable destinations, which the current dialog-only design avoided entirely. Accepted: this is required for the intercepting-route fallback to work, and `noindex` keeps them out of search results.
- **[Trade-off]** The Decision 11 bounce briefly flashes the plain full page before the two internal navigations land, and adds one extra history entry (`X`, then `/login?next=X`) compared to a true single intercepted navigation. Accepted: this is the cost of retrofitting the intercepted-modal experience onto a hard load; see the Open Question above for a possible follow-up.
- **[Trade-off]** Moving the auto-prompt's "already shown" tracking to in-memory module state (Decision 4) means it does not survive an actual tab close/reopen either (same as before, `sessionStorage` was tab-scoped too) - the only behavior change is that it now also does not survive a page refresh, which is the explicit intent (a refresh is a deliberate re-visit that should re-arm the prompt).
- **[Risk]** `useAuthNextParam()`'s own cleanup effect (which strips an invalid `next` value from the URL via `router.replace`, unchanged from Decision 2) is itself a soft navigation to the same `/login`/`/signup` pathname - and empirically, Next.js can apply the `(.)login`/`(.)signup` interception to that self-navigation too, showing the modal over the (unhelpful, since nothing meaningful changed) login page's own prior content rather than the plain full page, specifically for a hard load carrying an *invalid* `next` value. → Not fixed: doing so would mean changing `useAuthNextParam`'s cleanup mechanism away from the shared pattern it deliberately mirrors (Decision 2), for a rare adversarial-input edge case that does not weaken the actual security guarantee (the invalid value is still never navigated to, fetched, or rendered as a background - see the auth-route-modal spec's "An invalid return path is never used as a background target" requirement, worded to match this reality instead of overclaiming a specific visual shape for this one case).

## Migration Plan

1. Add the shared `isSafeInternalPath` validator (`src/lib/security/web/safe-redirect.ts`) and the `useAuthNextParam()` hook that wraps it (Decisions 2-3) - no behavior change on its own, unblocks everything else.
2. Add `login`/`signup` to `PUBLIC_ROUTES`, add `/login` and `/signup` full pages (reusing `LoginSignupLayout` + `LoginContent`/`SignupContent`, plus the `generateMetadata`/`robotsPreset` wiring from Decision 8), and the `@modal` intercepting pair reusing `LoginSignupPopup` (Decision 7), without yet removing the Zustand-driven popup - both can coexist since they render through different entry points (old popup is still triggered by the old store actions, new routes are reached only by new links).
3. Migrate call sites one at a time to the new navigation-based trigger (header button, `SignedInHomePage`, `BecomeInstructorPage`, the dashboard auto-prompt), running `gitnexus_impact` before each edit (Decision 10) and verifying each still round-trips through login/OAuth correctly.
4. Remove the old `LoginSignupPopup` Zustand wiring from `header.tsx`, `dashboard-layout.tsx`, `auth-layout.tsx`, and delete `authAction`/`nextLink` and their actions from `useAuthStore`.
5. Update the affected tests (`use-permissions.test.tsx` fixtures, `test-support/reset-stores.ts`, any test asserting on the old store shape).
6. Replace the outdated `LoginSignupPopup`/`authAction`/`nextLink` content in all eight `docs/*.md` files identified in Context with the new route-modal behavior, then run `gitnexus_detect_changes({ scope: "all" })` and `npx gitnexus analyze` to close out the change (Decision 10).
7. Add `useAuthModalBackgroundBridge()` / `AuthModalBackgroundBridge` (Decision 11) and mount it in `AppProviders`; verify a hard reload of `/login?next=<protected path>` shows the modal over the real background page, and that a plain `/login` (no `next`) is unaffected.
8. Swap the Decision 4 auto-prompt tracking from `sessionStorage` to the in-memory `autoPromptedPaths` module state; verify a genuine browser refresh of a denied dashboard route re-arms the prompt while a dismiss-triggered remount still does not.

Rollback is a plain revert of this change's commits; no data migration or persisted state is involved (the removed store fields were in-memory only).
