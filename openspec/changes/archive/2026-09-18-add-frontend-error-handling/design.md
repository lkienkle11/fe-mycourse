## Context

See proposal.md - Why. Today `fe-mycourse` has no `error.tsx` or `global-error.tsx` anywhere under `src/app`, and no component maps an API failure's status/kind to a distinct full-page UI. What already exists and this design builds on:

- `src/screen/common/not-found/not-found-page.tsx` (`NotFoundPage`) — the only existing full-page state: illustration + title + description lines + primary action button, rendered via next-intl server translations.
- `src/api/core/fetch-error.ts` — transport already classifies failures into distinct types: `ApiHttpError` (has `response.status`), `ApiNetworkError` (no response received), `ApiTimeoutError`, `ApiAbortError`, etc., plus `isApiHttpError` / `isApiTransportError` guards.
- `src/lib/utils/api-error.ts` — existing `extractApiError` / `toastApiError` pattern for mutation-triggered errors (toast only, not full-page); stays unchanged.
- Route groups live under `src/app/[locale]/{(web),admin,sysadmin,instructor}`; there is no segment-level error boundary at any level today.
- `lucide-react` (already a dependency, used e.g. in `dashboard-layout.tsx` for `Menu`/`X`) is the icon set already in use elsewhere in the app shell.

## Goals / Non-Goals

**Goals:**
- Catch render-time exceptions at the segment level (`[locale]/error.tsx`) and at the root level (`src/app/global-error.tsx`), so no failure mode reaches a blank page.
- Introduce one shared, variant-driven full-page component (`StatusErrorPage`) that covers `unauthorized` (401), `forbidden` (403), `server-error` (5xx), and `network` (unreachable/no response/timeout). A 404 or 429 response is explicitly out of scope for this component (see Decisions) and stays on the caller's existing generic fallback.
- Update `editor-page.tsx`'s course-detail failure branch (the concrete case already tracked as the Course-collaborator FE issue) to use `StatusErrorPage` instead of the generic "could not load" text, as the first real consumer proving the component out.

**Non-Goals:**
- Do not retrofit every screen in the app onto `StatusErrorPage` in this change — only `editor-page.tsx` is migrated; other screens adopt it incrementally later.
- Do not change `toastApiError` / mutation-error handling — that pattern is correct for user-initiated actions and is out of scope.
- Do not add a static HTML page served at the Nginx/VPS layer for total outages — that is infrastructure outside this repo's scope; this change only covers the in-app experience once a request to the API layer resolves to `ApiNetworkError` (backend TCP-unreachable, DNS failure, etc. while the frontend static assets still loaded).
- Do not change any BE contract, error code, or HTTP status mapping.
- Do not add a variant for a write-conflict-style status (e.g. 409) to `classifyApiError` — that classifier is specifically for the *primary GET-request* load a whole page depends on, and a 409 essentially never happens on a GET; it is a mutation-response status, which already has its own pattern (`toastApiError` + the numeric BE `errors.codes.*` system, see `docs/patterns.md` §6b). Adding it here would conflate the two error-UX systems this change deliberately keeps separate.

## Decisions

**One `error.tsx` at `[locale]/error.tsx`, not one per route group.** All four groups `(web)`, `admin`, `sysadmin`, `instructor` sit directly under `[locale]`; a single boundary there catches renders errors in any of them without duplicating the same fallback four times. A group-specific boundary can be added later only if a group needs bespoke recovery UI (none does today).

**`global-error.tsx` must own `<html>`/`<body>`.** Per Next.js App Router convention, `global-error.tsx` replaces the root layout entirely when it activates, so unlike every other error boundary it must render its own `<html>` and `<body>` tags and cannot assume `RootLayout`'s providers (fonts, `Toaster`) are mounted. Keep it deliberately minimal (no `NextIntlClientProvider`, no data fetching) so it cannot itself throw.

**`global-error.tsx` is locale-aware without the `NextIntlClientProvider`.** (Amended after the initial implementation shipped English-only, on request.) It cannot use `useTranslations` — no provider is mounted — but it can still show the right language: the existing `errors.boundary` messages are imported directly from `src/messages/{en,vi}.ts` as plain objects (no React context involved, so nothing new to throw), and the active locale is read from the URL's first path segment via `useSyncExternalStore` — the React-recommended primitive for reading external, non-React state like `window.location` without a hydration mismatch or a `setState`-in-`useEffect` anti-pattern (flagged by this repo's `react-hooks/set-state-in-effect` lint rule). `routing.defaultLocale` (`"vi"`) is the fallback both for the server/pre-hydration snapshot and for any path segment that isn't a recognized locale.

**`StatusErrorPage` is a client component generalized from `NotFoundPage`'s layout, not a copy-paste per variant.** One component takes `variant: "unauthorized" | "forbidden" | "server-error" | "network"` plus optional `title`/`description`/`action` overrides, and looks up its default icon/copy per variant. This keeps future variants a config addition, not a new file. `NotFoundPage` (route-level 404, server component, has its own illustration asset) stays separate since it renders before locale-scoped client state exists and already has a distinct visual (product illustration vs. status icon) — a 404 response from a primary data request is not modeled as a `StatusErrorPage` variant at all (`classifyApiError` resolves it to `"unknown"`), since this classifier has no reliable way to distinguish "resource not found" from any other unmapped status; a screen that needs that distinction reads its own response body, not this shared helper.

**Failure classification lives in one helper, reused by every screen — and is table-driven, not an `if`/`else` chain.** Add a `classifyApiError(error): StatusErrorVariant | "unknown"` helper alongside `extractApiError` in `src/lib/utils/api-error.ts`, using the existing `isApiHttpError`/`isApiTransportError` guards and `response.status` — so `editor-page.tsx` and future screens all resolve the same error the same way instead of re-deriving status-code-to-variant mapping per screen. (Amended, on request: the status→variant lookup moved from a growing `if (status === X) return Y` chain to an ordered `HTTP_STATUS_RULES` array of `{ status, variant }` / `{ minStatus, maxStatus, variant }` entries, resolved by a single `find()` — this is the intended scaling path the user asked for, adding a status code being a table entry rather than a new branch. `ApiTimeoutError` was folded into the `network` variant alongside `ApiNetworkError` at the same time, since a request that never got a response reads the same to an end user whether it failed outright or timed out; there is no separate `HTTP_STATUS_RULES` handling needed for transport-level errors since they never reach the status lookup. A `429 → "rate-limited"` entry was added then removed again in the same session, both on request — no `HTTP_STATUS_RULES` entry for 429 exists in the shipped version; it falls to `"unknown"` like any other unmapped status.)

**`useCourseDetail` callers must read `error`, not just `data`/`isLoading`.** `editor-page.tsx` currently destructures only `{ data, isLoading, mutate }`; the fix adds `error` to that destructure and branches on `classifyApiError(error)` before falling back to the current generic message (kept as the truly-unknown-cause fallback).

## Risks / Trade-offs

- [Risk] `global-error.tsx` re-implementing layout chrome (fonts, base styles) invites drift from `RootLayout` over time → Mitigation: keep it intentionally bare (plain HTML/CSS, no Tailwind theme dependency that could itself fail to load); covered by `src/app/global-error.test.tsx` (Jest) plus Next.js's own documented framework contract that `global-error.tsx` is invoked for any error escaping every segment boundary. (A live Playwright proof was tried and reverted — see tasks.md 4.2 — since it required an always-present test route and a production routing-config exception that exposed internal test tooling.)
- [Risk] A future contributor could be tempted to add a "not-found-data" variant next to the existing route-level `NotFoundPage`, confusing which one to use for a given 404 → Mitigation: deliberately not added; a 404 primary-request response stays out of scope for `StatusErrorPage`/`classifyApiError` (see Decisions) and uses the caller's own generic fallback instead.
- [Risk] Migrating only `editor-page.tsx` leaves other screens' generic fallbacks unchanged, so the fix is not felt everywhere at once → Mitigation: accepted per Non-Goals; `classifyApiError` + `StatusErrorPage` existing as reusable primitives is what unblocks incremental migration, tracked as future follow-up rather than blocking this change.
