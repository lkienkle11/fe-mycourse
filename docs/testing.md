# Frontend test coverage (`fe-mycourse`)

_Last updated: 2026-09-16 — Stage 1 (foundation), Stage 2 (priority business flows), and Stage 3 (browser runtime and bounded expansion) delivered under `openspec/changes/add-frontend-test-coverage`. This is selected-scope coverage, not whole-repository or exhaustive-file coverage._

## Harness — Jest (unit/integration)

- **Runner:** Jest via `next/jest` (`jest.config.ts`), driven by `JEST_PROJECT` env var:
  - `JEST_PROJECT=node` → Node environment. Matches `src/api/auth/**/*.test.ts` (except `browser-*.test.ts`), `src/api/transport/**/*.test.ts`, `src/app/api/auth/**/*.test.ts`.
  - Any other value (including unset) → jsdom environment. Matches `src/**/*.test.tsx`, `src/lib/**/*.test.ts`, `src/hooks/**/*.test.ts`, `src/store/**/*.test.ts`, `src/api/hooks/**/*.test.ts`, `src/schema/**/*.test.ts`, `src/events/**/*.test.ts`, `src/api/callers/**/*.test.ts`, `src/api/auth/browser-*.test.ts`.
  - A single canonical `jest.config.ts` (rather than two differently named files) is required so Knip's built-in Jest plugin — which only recognizes the literal `jest.config.{ext}` filename — can resolve `setupFilesAfterEnv` as a real entry point instead of reporting it as an unused file.
  - `next.config.ts` declares `transpilePackages: ["uuid", "next-intl", "use-intl", "@formatjs/fast-memoize", "@formatjs/icu-messageformat-parser", "@formatjs/icu-skeleton-parser", "@formatjs/intl-localematcher", "intl-messageformat", "@schummar/icu-type-parser", "icu-minify"]` — these ship ESM-only files, and `next/jest` only lets Jest transform node_modules packages listed there (its own default ignore rule cannot be relaxed from `jest.config.ts` directly).
  - `msw` is pinned to the exact version `2.11.1` (last release before `@mswjs/interceptors`/`msw` itself started depending on the ESM-only `rettime` package, which hits the same untransformable-node_modules limitation and has no workaround).
- **Libraries:** React Testing Library, `@testing-library/jest-dom` (via the `/jest-globals` entry point, for correct `@jest/globals` `expect` typing), `@testing-library/user-event`, MSW, `undici` (Fetch API polyfill for jsdom).
- **Known Jest/SWC limitation:** `jest.mock()` does **not** reliably hoist under this project's `next/jest` SWC transform (verified empirically) — a mocked module is still resolved to its real implementation by consumers that import it earlier in the module graph. Do not use `jest.mock()` for dependency substitution here. Use MSW to intercept HTTP boundaries, or constructor/prop injection where the code under test already accepts collaborators as parameters (e.g. `useCourseOutlineReorder`'s `acquireLease`/`releaseLease`/`mutateDetail`, `createMediaCallers`'s injected `ApiMethods`).
- **Setup files** (`src/test-support/`):
  - `jest.setup.node.ts` (Node `setupFiles`) — removes Node's unconfigured built-in `globalThis.localStorage` (breaks MSW's Node `CookieStore`, which checks `typeof localStorage` instead of `isNodeProcess()`).
  - `jest.setup.jsdom-encoding.ts` / `jest.setup.jsdom-fetch.ts` (jsdom `setupFiles`, in this order) — copy `TextEncoder`/`TextDecoder`/Web Streams/`MessageChannel`/`MessagePort`/`BroadcastChannel` from `node:*`, then `fetch`/`Request`/`Response`/`Headers`/`FormData` from `undici`, onto `globalThis` (jsdom implements none of these). `BroadcastChannel` specifically is required by MSW's WebSocket interceptor (`msw/core/ws`), which reads it at module-load time — omitting it throws `ReferenceError: BroadcastChannel is not defined` on every jsdom suite that imports the shared MSW `server`.
  - `jest.setup.ts` (`setupFilesAfterEnv`, both projects) — starts/stops the shared MSW `server` (`onUnhandledRequest: "error"`), resets Zustand auth/me store state, runs RTL `cleanup()`, and stubs `ResizeObserver`/`window.matchMedia`/pointer-capture/`scrollIntoView` (jsdom lacks them; Radix UI primitives probe them unconditionally).
- **Fixtures/helpers:** `src/test-support/render.tsx` (`renderWithProviders` — real `next-intl` messages + an isolated per-test SWR cache), `src/test-support/mock-app-router.tsx` (stub `AppRouterContext` for components calling `useRouter()`), `src/test-support/reset-stores.ts`, `src/test-support/fixtures/auth.ts` (`buildMeResponse`), `src/test-support/msw/server.ts`.
- **Commands:**
  - `npm test` — Node project then jsdom project, `--ci` (fails on zero discovered tests; no `--passWithNoTests`); jsdom runs with `--forceExit` (a React-scheduler `MessageChannel` handle — created because jsdom now has a real `MessageChannel`/`MessagePort` global for `undici`'s sake — otherwise keeps the process alive; harmless, not a test leak).
  - `npm run test:watch` — jsdom project in watch mode.
  - `npm run test:coverage` — both projects with `--coverage`, written to `coverage/node/` and `coverage/jsdom/` (gitignored; not added to ESLint's ignore list — the directory is absent on a fresh checkout, so ESLint never encounters it in CI).

## Harness — Playwright (browser)

- **Runner:** `@playwright/test` (`playwright.config.ts`), Chromium only, `workers: 1`, `fullyParallel: false` (serial — matches the design decision to reset shared fixture state between scenarios rather than introduce concurrency now).
- **Fixture backend:** `e2e/fixtures/server.mjs` — a plain `node:http` server (no framework), loopback-bound, serving the subset of the real BE contract the journeys need: `/api/v1/auth/login`, `/api/v1/auth/refresh` (upstream, called server-side), `/api/v1/auth/logout`, `/api/v1/me`, one synthetic course's detail/collaborators/instructor-candidates/collaborators-bulk (with two seeded outline sections)/sections-reorder/leases (acquire, heartbeat, release), and empty taxonomy lists. `POST /__fixtures__/reset` and `POST /__fixtures__/revoke-session` reset/mutate state between scenarios. Two synthetic accounts only (`instructor@example.test`, `learner@example.test`), never real credentials.
  - **CORS is required and easy to miss**: the browser calls this backend cross-origin (Next app and fixture backend are different ports). `credentials: "include"` alone is not enough — the fixture backend must also answer with an explicit (non-wildcard) `Access-Control-Allow-Origin` + `Access-Control-Allow-Credentials: true` and handle the `OPTIONS` preflight, or the browser discards every response before JS ever sees it. Confirmed by direct experiment: the first real run failed with exactly this (login cookies were set correctly, but `/api/v1/me` and every other client-side call silently failed).
  - **`Secure` cookies work over `http://localhost`**: `setAuthSessionCookies` sets `secure: NODE_ENV === "production"`, and `next start` always runs as `production`. Confirmed by direct experiment that Chromium treats `localhost` as a secure context for cookie purposes, so this does not need a workaround. Both the Next app and the fixture backend must be addressed as `localhost` (not `127.0.0.1`) — cookies are host-scoped but port-independent, which is what lets a cookie set by the Next app (one port) reach the fixture backend (a different port) at all.
- **Lifecycle:** `scripts/e2e-lifecycle.mjs` (`npm run test:e2e`) — starts the fixture backend in-process, runs `next build` with `NEXT_PUBLIC_API_URL` pointed at it (required: this env var is inlined at build time), starts `next start` on a fixed port, polls both for readiness, runs `playwright test`, then tears down both child processes on success **or** failure (verified: killed cleanly after both a passing and a failing run during development).
- **Journeys** (`e2e/tests/`), all passing against a real production build + real Chromium, verified with two consecutive clean runs:
  - `auth.spec.ts` — login grants access to a protected instructor screen; logout clears the session and shows the login control again; an expired/revoked session (simulated via `/__fixtures__/revoke-session`) logs the user out on the next check; a user without the required permission sees the "Access denied" state after logging in.
  - `course-editing.spec.ts` — adds a collaborator through the real picker UI (login → navigate to the collaborators tab → open picker → select the fixture candidate → confirm → appears in the list); reorders outline sections through a real keyboard-driven `@dnd-kit` drag (see below) and verifies the new order survives a page reload.
  - `locale-404.spec.ts` — a valid locale renders without an unhandled error; an unknown route under a valid locale shows the 404 page and its "Back to homepage" recovery link actually navigates home; an unsupported locale segment does not render as valid content or crash.
- **Outline drag-and-drop reorder is driven through the keyboard, not the pointer.** `SortableList` (`src/components/shared/sortable-list.tsx`) registers `@dnd-kit`'s `KeyboardSensor` as a first-class activation path alongside the pointer/touch sensors, not a fallback — focusing the drag-handle button and pressing Space picks the row up, `ArrowDown`/`ArrowUp` moves it among siblings, and Space drops it. `course-editing.spec.ts`'s "Course outline reorder" test drives exactly that sequence against two fixture sections and asserts the visual order, the persisted-order toast, and the order surviving a `page.reload()` (round-tripping through the fixture backend's `sections/reorder`/`leases/*` endpoints). This exercises the same `onDragEnd` → lease-acquire → persist → merge path (`src/hooks/course/use-course-outline-reorder.ts`) a pointer drag would, and is far more reliable across environments than simulating `@dnd-kit`'s multi-step pointer-sensor gesture. One real timing constraint was found and is commented in the test: `@dnd-kit`'s `KeyboardSensor` attaches its own keydown listener one tick after pickup, so the move key must not be sent in the same synchronous turn as the activating Space.
- **CI:** `.github/workflows/e2e-browser.yml` runs on pull requests to `dev`/`main` and pushes to `dev`: `npm ci` → `npm run test-all` → `npx playwright install --with-deps chromium` → `npm run test:e2e`, uploading `playwright-report`/`test-results` on failure. The existing `deploy-dev.yml` and `enforce-main-from-dev.yml` workflows are untouched. Hosted-CI verification is pending until a real GitHub Actions run is observed — this document records what runs, not a claim that it has been observed green on GitHub's infrastructure.
